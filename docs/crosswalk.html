FDOx to CIDOC CRM crosswalk

How the FDOx registry anchors harvested FDO metadata in CIDOC CRM, following the NFDI4Objects CIDOC-CRM in RDF application profile. Generated from crosswalks/fdo--crm.csv; edit the table, not this page.

A row is one of five kinds. axiom states something about a term in the FDOx or registry namespace and goes into metadata/crm_bridge.ttl. ext-axiom quotes a statement from an external ontology verbatim and names its source; nothing in this repository is invented about a namespace it does not own. normalise repairs an abbreviated class IRI that the generator writes and that resolves to nothing. instance is materialised per object when the bundle is built, because its subject is in a foreign namespace. none is a term left deliberately unanchored, with the reason beside it.

instance — 18 rows

TermKindTargetProfile / sourceNote
dcat:Catalog class crm:E31_Document The registry's own frame is anchored like everything else it publishes. A catalogue is a document about the objects it lists; E31 is a subclass of E73 Information Object, so the catalogue reaches CRM core by the same route as the FDOs in it.
dcat:CatalogRecord class crm:E31_Document One document per pinned version, documenting one FDO. See foaf:primaryTopic for the relation itself.
dcat:Dataset class crmdig:D1_Digital_Object Materialised rather than relied upon: six of seven packages write crm:E73 and crmdig:D1 themselves in abbreviated form and the normalise rows repair them, but a package that writes neither would otherwise enter the catalogue without an anchor and the gate would find it only afterwards.
dcat:Distribution class crmdig:D9_Data_Object Materialised per distribution. The generator already writes the abbreviated crmdig:D9, which the normalise rows repair; this row covers distributions that carry no CRMdig type at all.
dcat:keyword@iri property crm:P2_has_type section 3 Only the IRI-valued keywords. The string-valued ones are a separate row.
dct:PeriodOfTime class crm:E52_Time-Span Materialised per instance. The node the generator hangs dcat:startDate and dcat:endDate on is the time-span itself; without the type a CRM consumer sees P4 pointing at something untyped. The class is not what the profile objects to - it objects to expressing the temporal value through P82a/P82b instead of a literal, and that literal is written as well.
dct:description property crm:P3_has_note Repeatable, so all four descriptions per FDO (A1, Befund 5) are carried and none is chosen. Which of them is the real description is a question for the quality report, not for the mapping.
dct:provenance property crm:P3_has_note Carries a JSON string, not a structure. D2 Digitization Process and P16 used specific object have no source to be built from - see the note on technique.acquisition.
dct:spatial property crm:P67_refers_to The FDO refers to the place; it does not happen there, so P7 took place at would be wrong - an information object is not an event. The object is typed crm:E53_Place by the object-class row below.
dct:spatial@object object-class crm:E53_Place Types the object of dct:spatial, which is an OpenStreetMap IRI in every package. Per instance, never as an axiom: nothing is asserted here about what OpenStreetMap relations are in general, only that these seven are places. Without it P67_refers_to points at an untyped node.
dct:subject property crm:P2_has_type section 3 Duplicates dcat:keyword in every harvested package, IRIs and strings alike.
dct:temporal property crm:P4_has_time-span section 2 Temporal data Two statements, both profile-conform. The dct:PeriodOfTime node keeps its structure and is typed crm:E52_Time-Span; beside it the FDO carries the temporal value as the typed literal the profile asks for: xsd:gYear where start and end are equal, otherwise an EDTF level-0 interval such as 0300/0699. The source writes xsd:integer, which the profile does not list as a temporal data type (Befund 15).
dct:title property crm:P102_has_title section 4 E41 Literal object. E35 Title is avoided as the profile requires; the profile's own example uses P102 with a plain literal.
dct:type property crm:P2_has_type section 3 Object is an external concept IRI (Wikidata, in one package an OpenStreetMap relation).
foaf:primaryTopic property crm:P70_documents The CRM reading of what a catalogue record is: an E31 Document that documents the FDO. Runs beside foaf:primaryTopic, which stays as DCAT expects it.
schema:Organization class crm:E74_Group section 6 As schema:Person. The only organisation in the corpus is the Research Squirrel Engineers Network under its Wikidata IRI.
schema:Person class crm:E21_Person section 6 Foreign namespace: materialised per instance, never axiomatised (A3). The profile's bridge axioms cover foaf: and dcterms:, not schema:.
sf:Point@instance class crmgeo:SP5_Geometric_Place_Expression section 2 Spatial data The profile replaces E94 Space Primitive with a GeoSPARQL geometry and points at CRMgeo for the CRM side of that bridge. A WKT point in a coordinate reference system is precisely an SP5 Geometric Place Expression, so typing these seven nodes gives the geometry a CRM anchor without asserting anything about geo:Geometry in general.

Role vocabulary

The values fdo:role takes on a distribution, as SKOS concepts in https://w3id.org/fdo-squirrel/registry/role/. The list is flat: the packages draw no hierarchy between the values, and inventing one would put structure into the registry that its sources do not carry. Counts are occurrences in the harvested packages the registry can read.

Packages the registry cannot read

The registry reads, it does not correct. A harvested fdo-metadata.ttl that is not valid Turtle is skipped with a reason and reported here and in the quality report; the fix belongs in the generator that wrote it, not in the registry that reads it.
