Query the registry

The whole catalogue is one Turtle file, and this page runs SPARQL over it in your browser. Every query below is editable: change it, press Run, and see what the graph actually says rather than what the tiles on the front page chose to show.

Release 2026-09-03 · 6584 triples · Catalogue · CRM crosswalk · Query

There is no SPARQL endpoint and no server behind this page. The catalogue is fetched as a static Turtle file — dist/fdo-registry.ttl, the same file the front page offers for download — and parsed in your browser with rdflib 7.1.1 under Pyodide 0.26.4. Nothing you type leaves your machine, and an archived copy of this repository stays queryable with no service kept alive for it. The first visit downloads about 10 MB of Python runtime.

1. Every FDO with its type, licence and file count

The list the catalogue exists for. One row per FDO, counted from the catalogue node outwards, so an entry that has lost its link to the catalogue disappears here rather than quietly staying in the tiles.

7 rows when this page was built · catalogue-overview.rq

2. 3D models with their coordinate, as WKT

The column ?wkt is a GeoSPARQL literal with its CRS in front, so the result can be pasted into QGIS as delimited text without further conversion. The point is the one the package states — for several of these objects that is the centroid of a country, not the find spot.

5 rows when this page was built · models-with-coordinates.rq

3. Every 3D model file, with format, size and role

fdo:role stays in the bundle as the literal the package wrote, and beside it stands crm:P2_has_type on a SKOS concept. The label of that concept is not in the bundle, so this query loads the role vocabulary as well — which is exactly the difference between a value and a term.

Also loads the registry vocabularies (about 95 triples, loaded from this site): those statements are deliberately not in the published bundle, so this query needs them beside it.

12 rows when this page was built · model-files.rq

4. Wikidata concepts that more than one FDO points at

What the packages have in common, in their own words. This is the query that would show a subject vocabulary drifting apart: two packages meaning the same thing and saying it with two different Q-ids appear here as two rows of one, not as one row of two.

2 rows when this page was built · shared-concepts.rq

5. Every creator, over all packages

Counted per node, not per name, and that is the point: the same person appears twice here, once with an ORCID and once as a registry agent IRI, because the older packages carry ORCIDs and the newer ones a package-local person URN. The catalogue page merges the two by name; the graph does not, because merging identity on a name is a claim no package makes.

5 rows when this page was built · creators-across-packages.rq

6. Holdings by licence

The licence is an SPDX IRI in the graph; the short id in the result is derived here the same way the catalogue page derives its facet, so the two numbers can be compared. If they ever disagree, one of them is wrong.

4 rows when this page was built · holdings-by-licence.rq

7. Holdings by year of publication

The year the FDO was published, falling back to the creation date where a package states none — not the period of the object it describes. Five of seven packages carry the same Ogham date range, so the object's period makes a poor facet and a good column.

5 rows when this page was built · holdings-by-year.rq

8. Every class in the catalogue and how it reaches CIDOC CRM

The claim of PRIMER A2, as a table anyone can re-run. Two columns, because there are two mechanisms: a class in our own namespace may be anchored by an axiom in the bridge, and everything else is anchored on each instance, since this registry does not make axiomatic statements about namespaces it does not own. A CRM class needs no anchor — it is one — and the owl:* rows describe the vocabulary files themselves rather than anything in the catalogue.

Also loads the registry vocabularies (about 95 triples, loaded from this site): those statements are deliberately not in the published bundle, so this query needs them beside it.

24 rows when this page was built · crm-anchors.rq

The queries on this page come from queries.yaml in the repository and are executed against this bundle whenever the site is built; a query that returns nothing fails that build. The same queries are in docs/downloads/queries/ as plain .rq files, with the prefix block included, for use against any other SPARQL processor.
